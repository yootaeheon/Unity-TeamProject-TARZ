# **Ⅱ**. 구현 컨텐츠

# **1. BehaviorDesigner를 이용한 몬스터 AI 구현**

## 1.1 구상

- 플레이어가 인지 범위에 들어올 시 추격하여 공격 범위 내 도달 시 공격
- 엘리트, 보스 몬스터는 조건이 가능할 시 스킬 시전

## 1.2 설계 방법

### **Behavior Designer 사용하여 몬스터 AI 구현**

- **구현 기술**
    - 실제로 행동을 수행하는 Action 노드, 행동의 조건을 확인하는 Condition 노드를 구현
    - 일반 몬스터의 기본 노드 + 특수 노드(스킬, 추적 방법) 등을 조합하고 순서를 새롭게 배치하여 11종의 몬스터 생성
    - 몬스터의 이동은 장애물을 피하여 플레이어를 추격해야 하므로 Navigation System 사용하여 구현
    - 대부분의 기능은 애니메이션과 매서드 타이밍을 일치시키기 위하여 애니메이션 이벤트를 사용하여 구현
- **이 방식을 사용한 이유**
    - 재사용성
        - 1개의 기능 단위로 노드를 구현하여 새로운 조합/배치만으로 여러 종류의 새로운 종류의 몬스터를 생성할 수 있음
        - 즉, 노드를 재활용하며 새로운 몬스터를 쉽게 생성 가능
        
### **내적 연산을 이용한 근접 공격**

- **구현 기술**
    - 근접 공격 실행 시 설정한 Range만큼의 크기로 Overlap을 실행하여 주위에 있는 적을 탐지
    - 내적 연산을 계산하여 탐지된 적과 자신의 각도 차이가 설정한 Angle 범위 내라면 Hit 판정
- **이 방식을 사용한 이유**
    - 판정 정확도 향상
        - Collider의 충돌로 근접 공격을 구현했을 시 오브젝트 간의 높이 차이가 있었을 때 Hit 판정이 나지 않는 등의 판정에 어려움이 있음
        - 또한 공격마다 원하는 판정 범위와 거리를 설정하기 위하여 내적 연산 이용
        
### **몬스터가 특정 범위 내에서 적(플레이어)을 감지할 수 있도록 시야와 거리, 장애물 여부를 기반으로 적을 인지하는 기능을 구현**

- **구현 기술**
    - 내적 연산을 사용하여 몬스터의 전방 벡터와 적 사이의 방향 벡터를 비교해 시야 범위에 있는지 확인
    - 인지 각도와 거리는 직렬화를 통해 인스펙터에서 수치 조정 가능
        
- **이 방식을 사용한 이유**
    - 몬스터의 다양성
        - 몬스터가 플레이어를 추격할 수 있는 인지 범위를 거리와 각도를 각각 설정하기 위하여 LineCast와 내적 연산을 사용하여 구현
    - 판정 정확도 향상
        - LineCast를 이용하여 몬스터와 대상 사이에 장애물이 있는지 판별과 동시에 충돌체가 적의 자식 오브젝트인 경우에도 감지 했다고 판단하여 정확성을 높일 수 있음
    - 최적화
        - 거리와 시야각을 먼저 검사 후 성능 소모가 큰 LineCast를 최소한으로 호출하여 성능 저하를 방지
    - RayCast가 아닌 LineCast 사용
        - LineCast는 두 점 사이의 구간만 검사하므로, 불필요한 추가 연산을 방지하고자 사용
        - 적을 인지하는 로직에서는 플레이어와 적 사이의 "가시성"을 판단하는 것이 주 목적이므로, RayCast 보다는 두 점 간 충돌 여부를 검사하는 LineCast가 직관적이어서 적합하다고 판단

### **Zenject로 몬스터 팩토리, 오브젝트 풀 패턴 적용**

- **구현 기술**
    - 몬스터 팩토리 인스톨러에서 각각의 몬스터 게임 오브젝트를 다른 아이디로 받아 팩토리들을 바인딩하여 컨테이너화
    - 오브젝트 풀 클래스에서 컨테이너를 바인딩하여 ResolvedId로 팩토리들을 가져와 List에 추가
    - List를 불러와 몬스터 이름으로 소환가능하며 몬스터 종류와 수를 지정하여 원하는 위치에서 생성 가능
        
- **이 방식을 사용한 이유**
    - 최적화
        - 몬스터의 생성/파괴로 인한 성능 저하를 고려하여 활성화/비활성화로 대체하는 오브젝트 풀 패턴 적용
    - 의존성 주입
        - 몬스터에게 플레이어를 Inject(의존성 주입) 하는 과정에서 나중에 생성되는 몬스터에게 주입이 안 되는 문제로 인하여 **Zenject**로 몬스터 팩토리를 구현
    - 왜 List를 사용하였는가
        - List는 데이터 접근에 특화되어 있어, 순차적으로 인덱싱이 가능하기 때문에, 몬스터의 이름을 인덱스로 변환하여 특정 몬스터에 종류에 바로 접근할 수 있어 간단하고 직관적임
        - 큐를 사용해도 구현은 가능하나 몬스터의 종류 선택하여 풀링해야하기 때문에 부적합
        - 추후 다른 종류의 몬스터가 추가될 가능성에 대비하여 List를사용

### **몬스터 스킬 구현**

- **구현 기술**
    - MonsterSkillManager 클래스에서 스킬을 호출하는 방식으로 구현
    - 스킬은 쿨타임 체크를 위하여 코루틴으로 구현
    - 각 스킬의 데이터는 ScriptableObject를 생성하여 관리
        - 스킬 이름, 데미지, 쿨타임, 공격 범위, 각도, 점프 시간, 점프 거리 등 모든 정보를 수정 가능
        - MonsterSkillManager에서 각 스킬의 ScriptableObject를 참조 연결하여 수치를 연동하고 있음
    - 점프 스킬은 코루틴과 삼각함수의 Sin 함수를 이용하여 Transform 이동시키는 방식으로 구현
        
- **이 방식을 사용한 이유**
    - 재사용성과 확장성
        - BehaviorDesigner에서 각 스킬을 노드로 생성하여 같은 로직의 스킬을 재사용하여 사용 가능하며 스킬 유지보수와 확장성에 용이함
    - 데이터 관리
        - 스킬 데이터는 런타임 중 변하지 않는 ScriptableObject로 관리하여 기획자가 테스트하며 쉽게 밸런싱 가능
    - Transform을 사용 이유
        - Rigidbody를 이용하여 물리 기반으로 구현하였으나 Navigation System 작동 중 물리 처리가 적용되지 않기 때문에 Transform 이동시켜주는 방식을 선택택

### **저스트 회피 기능 구현**

- **구현 기술**
    - 몬스터가 공격 시작 시 플레이어가 유효한 거리와 각도 내에 있으면 회피 Trigger를 활성화 후 회피 타이밍이 종료되면 Trigger 비활성화
        - LineCast와 내적 연산을 이용하여 플레이어가 범위 내에 있을 시 bool 반환값이 True 반환
        - 애니메이션 이벤트로 함수를 호출하여 원하는 타이밍에서 함수 호출
    - Trigger가 활성화되어 있을 때 플레이어가 대쉬 기를 이용하여 Trigger를 빠져나가는 경우 몬스터의 티어에 따른 지정된 반격 수행
- **이 방식을 사용한 이유**
    - 기능 오작동 예방
        - Trigger만 사용하였을 때, 플레이어가 몬스터의 뒤에 있을 때에도 Trigger가 활성화/비활성화 되며 기능이 오작동하는 경우가 생길 수 있음,  LineCast와 내적 연산을 통하여 플레이어가 몬스터의 (전방) 공격 범위에 있을 시에만 Trigger 활성화/비활성화
        
### **몬스터의 피격은 IDamagable 인터페이스를 사용하여 구현**

- 확장성
    - 몬스터뿐만이 아닌 플레이어, 오브젝트 등 다른 피격 가능한 요소에서 동일한 방식으로 적용하기 위해 인터페이스를 사용
- 유지보수성
    - 모든 피격 로직이 동일한 인터페이스에서 수행되므로 기능을 추가/수정 하는 부분에서 유지보수성 향상

### **몬스터 데이터 MVP 패턴 적용**

- **구현 기술**
    - 모델과 뷰 컨트롤러를 각각의 클래스로 분리하여 몬스터의 체력 바 같은 UI에 실시간으로 변하는 데이터를 정확하게 연동
        
- **이 방식을 사용한 이유**
    - 정확성
        - MVP 패턴을 통해 각 클래스의 역할을 명확히 분리하여, 각각의 컴포넌트를 독립적으로 테스트 및 유지보수 가능하며 오차 없이 연동 가능
    - 유지보수성
        - MVP 패턴을 통해 각 클래스의 역할을 명확히 분리하여, 각각의 컴포넌트를 독립적으로 테스트 및 유지보수 가능

- **모든 수치 데이터 직렬화**
    - **구현 기술**
        - 몬스터의 모든 수치 데이터를 직렬화하여 인스펙터 창에서 수정 가능
    - **이 방식을 사용한 이유**
        - 쉽게 테스트하며 밸런싱 가능하게 구현
            

### Gizmo **시각화로 범위 설정 간편화**

# **2. 절차적 맵 생성 구현**

## 2.1 구상

- 씬 로드 시 랜덤한 맵을 생성하는 기능 구현
- 각 구역을 분리하여 다른 구조의 장애물과 몬스터 생성
- 상점과 보스룸 생성

## 2.2 설계 방법

### **씬 로드 시 프리팹을 가지고 랜덤한 맵을 생성하는 기능 구현**

- **구현 기술**
    1. 랜덤한 방향으로 진행
    2. 비어 있다면 빈 방 생성
    3. 몬스터 스포너 레이어
    4. 장애물 레이어
    5. WallDestroyer가 진행 방향을 뒤따라가며 막힌 벽을 비활성화
    6. 설정한 RoomCount 만큼 1~5번 반복하여 맵 생성
    7. 보스 방 생성
    8. 상점 생성
    
    - 빈 방 프리팹을 생성 후 레이어링 할 게임 오브젝트 배열들 중 한개씩 랜덤으로 생성하여 쌓는 방식
        
### **절댓값을 사용한 보스 방, 상점 위치 찾기**

- **구현 기술**
    - Mathf.Abs() 함수를 사용하여 생선한 맵의 X,Z 값의 절댓값 크기를 비교
    - 절댓값이 가장 큰 방을 보스 룸 생성 진행 위치로 지정
    - 더 작은 값을 상점 생성 진행 위치로 지정
- **이 방식을 사용한 이유**
    - 큰 줄기(보스 방으로 향하는 길)와 잔 가지(갈래 길) 같은 맵을 기획팀에서 요청
        - 보스 방으로 가기 위한 명확한 방향성을 구현하고자 절댓값을 이용하여 구현
    

### **진행 방향의 벽 비활성화**

- **구현 기술**
    - WallDestroyer 게임 오브젝트가 맵이 생성되는 방향으로 뒤따라가며 Wall 태그의 오브젝트에 Trigger시 비활성화
- **이 방식을 사용한 이유**
    - 최적화
        - 게임 특성 상 벽을 열고 닫고를 반복하는 과정에서, 생성/파괴 과정 최적화를 위하여 활성화/비활성화 방식 선택
        

### **빈 방 여부 체크**

- 겹치는 위치에 방 생성을 방지하기 위해 RoomChecker 클래스 생성
- OverlapSphere 사용하여 RoomChecker 게임 오브젝트의 설정한 범위 내에 오브젝트가 있다면 return false 반환

### **구역 폐쇄/개방**

- **구현 기술**
    - 플레이어가 구역에 진입 시 몬스터 스포너에 Trigger 되었을 때 몬스터 생성 및 CloseWall() 함수가 호출되며 구역 폐쇄
    - WallDestroyer가 비활성화 시킨 벽을 배열로 받아오며 다시 활성화 시키며 구역 클리어 시 OpenWall() 함수 호출되며 배열에 담은 활성화 한 벽을 다시 비활성화
- **이 방식을 사용한 이유**
    - 동적 관리 가능
        - 벽의 활성화/비활성화를 배열로 관리하여, 인덱스를 통해 빠른 접근으로 쉽게 동적 폐쇄 및 개방 로직을 구현할 수 있음.
    - 최적화
        - 벽 개수가 구역마다 정해져 있어 크기가 고정된 배열을 사용하여, 실행 중 데이터 크기를 동적으로 늘리거나 줄일 필요가 없어 빠른 접근 속도와 성능적 이점을 가짐
        
### **옵저버 패턴을 이용한 구역 클리어 조건**

- **구현 기술**
    - 풀링된 몬스터가 사망 시 OnDie 이벤트를 발생 시켜 MonsterCountChange() 매서드를 호출하는 이벤트 사용
- **이 방식을 사용한 이유**
    - 최적화
        - 로직을 매프레임마다 확인하는 업데이트가 아닌 이벤트 기반으로 구현하여 불필요한 연산을 최소화하고자 이벤트 기반으로 구현
    - 확장성과 유지보수성
        - 몬스터 처치와 문 열림 로직을 분리하여 각각 독립적으로 관리할 수 있고 추가적인 기능 필요시에 확장성을 확보함

# **3. 사운드 매니저 구현**

## 3.1 구상

- ScriptableObject의 데이터를 사운드 매니저를 통하여 직관적인 호출
- 오디오 클립을 ID로 구분하여 사운드 재생

## 3.2 설계 방법

### **사운드 데이터를** ScriptableObject**로 구현**

- **구현 기술**
    - 사운드 데이터를 구조체로 선언 후 직렬화하여 오디오 클립을 참조
    - 각 참조된 오디오 클립을 프로퍼티로 읽기 전용 접근 가능
    - 사운드 매니저에서 사운드 데이터를 참조하고있어 직관적 사용이 가능
- **이 방식을 사용한 이유**
    - 확장성과 유지보수성
        - 각 분야의 사운드를 한 곳에서 관리하여 유지보수에 용이하며 다른 추가적인 사운드가 필요할 경우 추가가 편함
        

### **몬스터 고유 사운드를 ID로 구분하여 재생**

- **구현 기술**
    - 몬스터 사운드 데이터에 SoundInfo 구조체를 생성하여 ID와 오디오클립 변수 선언
    - 몬스터 모델에 행동에 맞는 사운드 ID와 오디오클립을 참조
    - 예를 들어 A몬스터가 공격, 피격 사운드 재생 시에 A몬스터의 공격, 피격 사운드 ID에 맞는 오디오 클립 재생
- **이 방식을 사용한 이유**
    - 확장성
        - 같은 코드로 몬스터마다 다른 사운드를 재생해야 하므로 조건문으로 구분하여 재생하는 대신 각 몬스터의 사운드 ID를 판별하여 재생
    - 구조체 사용 이유
        - 데이터 저장소 용도로 사용하기 위해서 구조체 사용
        - 관련된 데이터를 그룹화하여 가독성을 높이고 데이터 관리의 일관성을 유지하기 위함
        - 직렬화를 통하여 인스펙터 상에서 오디오 클립을 직접 참조하기 위해 구조체 사용
        
### **사운드 매니저는 싱글톤으로 구현**

- 싱글톤으로 구현하여 참조 없이 전역적인 접근이 가능
- 게임 내의 모든 사운드 기능을 단일 인스턴스가 관리하므로 유지보수에 좋음
- Zenject를 통하여 구현하려 했지만, 나중에 생성되는 오브젝트들에 Zenject를 통한 의존성 주입이 적용 되지 않기 때문에 싱글톤으로 구현

## 1. **Navigation System 동작 중 물리 기반 점프 미작동 문제**

### 원인

몬스터는 기본적으로 플레이어를 추격하는 과정에서 장애물을 피해서 갈 수 있는 Navigation System을 이용하여 움직임을 구현하였음

몬스터의 스킬 중 점프를 하는 스킬을 Rigidbody 클래스를 사용하여 물리 기반으로 구현하였으나 동작하지 않는 문제가 발생

**Navigation System 동작 중**에 **물리 처리가 적용되지 않는** 원인 확인

### 해결 방법

점프 로직을 물리 기반이 아닌 Transform을 이동시키는 방식으로 로직 변경

Mathf.Sin 함수를 이용하여 **삼각함수 Sin** 그래프의 0 ****~ π(파이) 까지 그래프를 활용하여 구현


## 2.  ****맵 생성 과정 중 폐쇄된 공간이 생기는 문제

### 원인

맵을 생성하는 과정은 랜덤한 방향으로 진행하며 맵 프리팹을 쌓고 진행 방향의 벽을 제거하는 방식으로 생성됨

랜덤한 방향으로 진행되다 보면 같은 좌표에 맵 **프리팹이 겹치게 생성**될 수 있는 문제가 생기며, 이때 **폐쇄된 공간**이 생기는 문제 또한 발생


### 해결 방법

동일 좌표 맵 겹침 생성과 폐쇄된 공간을 방지하기 위해 **RoomChecker** 클래스를 생성

RoomChecker 게임 오브젝트는 **OverlapSphere** 를 사용하여 설정한 범위 내에 오브젝트가 있다면 return값을 false로 반환하여 다른 방향으로 진행하게 만듬

같은 좌료포 돌아와 프리팹을 겹치게 생성하는 문제와 이로 인한 폐쇄 공간이 생기는 문제를 해결
